# LcView Daemon 服务

## 概述

`lechao_lcview` 是 lechao vendor 的**结构化日志打点框架**的 system 域 Daemon 进程，通过 Binder AIDL `getBatch()` 从 HAL（vendor 域）拉取批量二进制数据，经 `SchemaParser` 逐字段校验后由 `FileWriter` 按事件 ID 分文件写入 JSONL 格式到本地磁盘。

- **职责**：数据校验层 + 持久化层——从 HAL 拉取二进制数据，按 Schema 校验字段类型和数量，合法记录按事件 ID 写入独立 JSONL 文件
- **进程域**：system 域常驻进程，由 `lechao_lcview.rc` 启动
- **数据源**：通过 vndbinder 连接 `vendor.lechao.lcview.ILcView/default` HAL 服务

**设计理念：** Pull 模式对比 Push 回调更健壮——daemon 崩溃重启后直接调 `getBatch()` 无需重新注册回调；daemon 处理慢时自然形成背压，数据在 HAL 内部排队；无 DeathRecipient 生命周期管理。

**设计目标：**

1. **Pull 模式健壮** — daemon 通过 `getBatch()` 无状态拉取，对比 Push 回调模式无回调生命周期管理、无死亡监听、无背压缓冲
2. **Schema 驱动校验** — 每个事件 ID 对应固定字段 schema（JSON 配置），daemon 逐字段校验类型和数量，不合法记录拒绝落盘
3. **按 ID 分文件** — 不同 event_id 写入独立 JSONL 文件，便于云端一对一建表和前端查询
4. **自动滚动** — 按时间（每天）+ 大小（50MB）双重滚动，总占用超限自动删除最旧文件

**源码路径：**

- AOSP 源码根目录：`~/workspace/aosp`
- Daemon 源码目录：`vendor/lechao/services/lechao_lcview/daemon/`
- 完整源码归档：[`../../code/rpi5/aosp/new/vendor/lechao/services/lechao_lcview/daemon/`](../../code/rpi5/aosp/new/vendor/lechao/services/lechao_lcview/daemon/)

> **关联文档：** HAL（vendor 域）设计见 [01.02-HAL增强-lcview-hal](./01.02-HAL增强-lcview-hal.md)。内核打点 API 设计见 [01.01-内核态增强](./01.01-内核态增强-lcview-kernel.md)。系统级架构分析见 [README.md](./README.md)。

## 用例视图

### 正常路径：数据校验与落盘生命周期

二进制数据从 HAL 拉取到写入磁盘的完整生命周期：

```plantuml
@startuml
autonumber
participant "HAL (vendor域)" as HAL
participant "main Loop\n(daemon主线程)" as MAIN
participant "SchemaParser\n校验引擎" as SCHEMA
participant "FileWriter\n持久化层" as FW
participant "/data/vendor/lechao_lcview/logs/" as DISK

HAL -> MAIN : Binder: getBatch()
note right of MAIN: 阻塞等待数据\n最多 1s
MAIN -> MAIN : batch = byte[]

loop 逐条记录解析
    MAIN -> MAIN : parse 4B len + record
    MAIN -> SCHEMA : validate(record, len, errMsg)
    SCHEMA -> SCHEMA : magic == 0x4C56?
    SCHEMA -> SCHEMA : event_id exists?
    SCHEMA -> SCHEMA : field_count matches?
    SCHEMA -> SCHEMA : 逐字段类型校验
    alt 校验通过
        SCHEMA --> MAIN : true
        MAIN -> FW : writeRecord(schema, hdr, fields)
        FW -> DISK : JSONL 写入
        FW -> FW : ALOGI("write...")
        note right of FW: 立即 flush\n防止崩溃丢数据
    else 校验失败
        SCHEMA --> MAIN : false + errMsg
        MAIN -> FW : writeInvalid(data, len, errMsg)
        FW -> DISK : invalid_records.log
    end
end

MAIN -> FW : checkRotation()
MAIN -> FW : enforceRetention()
@enduml
```

### 异常路径

#### Schema 文件未就绪

vendor 分区可能在 daemon 启动后才挂载完成，schema 加载需要重试：

```plantuml
@startuml
participant "daemon main()" as MAIN
participant "/vendor/etc/lcview_events.json" as JSON

loop 最多 30 次 (每次间隔 500ms)
    MAIN -> JSON : loadFromFile()
    alt 文件存在且合法
        JSON --> MAIN : 成功
        MAIN -> MAIN : schema.eventCount()
    else 文件不存在或损坏
        JSON --> MAIN : 失败
        MAIN -> MAIN : sleep 500ms
        note right of MAIN: schemaRetry++
    end
end

alt 30 次后仍未加载
    MAIN -> MAIN : ALOGE + return 1
else 加载成功
    MAIN -> MAIN : 继续
end
@enduml
```

#### HAL 服务未就绪

HAL 进程可能在 daemon 启动后才注册服务，需要优雅重试：

```plantuml
@startuml
participant "daemon main()" as MAIN
participant "ServiceManager" as SM
participant "HAL 进程" as HAL

loop 最多 1200 次 (每次间隔 100ms)
    MAIN -> SM : AServiceManager_checkService("vendor.lechao.lcview.ILcView/default")
    alt 服务已注册
        SM --> MAIN : AIBinder*
        MAIN -> HAL : ILcView::fromBinder()
        HAL --> MAIN : hal 实例
    else 服务未注册
        SM --> MAIN : nullptr
        MAIN -> MAIN : sleep 100ms
        note right of MAIN: retryCount++
    end
end

alt 1200 次后仍未连接
    MAIN -> MAIN : ALOGE + return 1
else 连接成功
    MAIN -> MAIN : 进入主循环
end
@enduml
```

#### Binder 连接中断

HAL 崩溃或 ServiceManager 不可用时重连：

```plantuml
@startuml
participant "daemon main loop" as LOOP
participant "HAL (Binder)" as HAL

LOOP -> HAL : getBatch()
alt Binder 通信正常
    HAL --> LOOP : status.isOk()
else Binder 异常
    HAL --> LOOP : !status.isOk()
    note right of LOOP: 可能是 HAL 重启\n或 ServiceManager 不可用
    LOOP -> LOOP : sleep 1s
    LOOP -> HAL : bind_hal() 重连
    alt 重连成功
        HAL --> LOOP : hal 实例
        LOOP -> LOOP : continue 主循环
    else 重连失败
        HAL --> LOOP : nullptr
        LOOP -> LOOP : ALOGE + break
    end
end
@enduml
```

#### 磁盘空间不足

总日志量超限时删除最旧文件腾空间：

```plantuml
@startuml
participant "FileWriter::enforceRetention()" as FW
participant "logs 目录" as DIR
participant "最旧文件" as OLD

FW -> DIR : opendir() + readdir()
FW -> FW : 收集所有 .jsonl/.log 文件
FW -> FW : sort by mtime (升序)
FW -> FW : 计算 totalSize

loop totalSize > maxBytes (500MB)
    FW -> OLD : unlink()
    note right of OLD: 最旧文件分析价值最低
    FW -> FW : totalSize -= size
end

FW -> DIR : closedir()
@enduml
```

### 二进制记录格式

```plantuml
@startuml
rectangle "4B 长度前缀\n----\ntotal_len (uint32_t)" as LEN
rectangle "16B 记录头\n----\nmagic (2B) = 0x4C56\nevent_id (2B)\nlevel (1B)\nfield_count (1B)\nreserved (2B)\ntimestamp_ns (8B)" as HDR
rectangle "字段区\n----\nfield[0]: type(1B)+value\nfield[1]: type(1B)+value\n..." as BODY

LEN -right[hidden]-> HDR
HDR -right[hidden]-> BODY
@enduml
```

**字段编码表：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `magic` | `uint16_t` | 魔数 `0x4C56` ('LV')，用于快速校验数据完整性 |
| `event_id` | `uint16_t` | 事件类型 ID，映射到 JSON schema 定义 |
| `level` | `uint8_t` | 日志级别 (0=DEBUG, 1=INFO, 2=WARN, 3=ERROR) |
| `field_count` | `uint8_t` | 字段数量，必须与 schema 中定义的字段数一致 |
| `reserved` | `uint16_t` | 保留字段，对齐用 |
| `timestamp_ns` | `uint64_t` | 内核打点时的纳秒时间戳 (`ktime_get_real_ns()`) |

**字段值编码：**

| type | 值格式 | 说明 |
|------|--------|------|
| `LCVIEW_TYPE_INT32 (1)` | 4 字节定长 | 有符号 32 位整数 |
| `LCVIEW_TYPE_INT64 (2)` | 8 字节定长 | 有符号 64 位整数 |
| `LCVIEW_TYPE_FLOAT (3)` | 4 字节定长 | IEEE 754 单精度浮点 |
| `LCVIEW_TYPE_STRING (4)` | 2B 长度 + UTF-8 文本 | 变长字符串 |
| `LCVIEW_TYPE_BINARY (5)` | 2B 度 + 原始字节 | 变长二进制数据 |

### JSONL 输出格式

每行一个 JSON 对象，不含字段名，`f` 数组按 schema 顺序排列：

```jsonl
{"ts":1738900000123456789,"id":4,"level":1,"f":[0,1,4096]}
{"ts":1738900001123456789,"id":5,"level":1,"f":[0,1,4096,12345678,0]}
```

| 字段 | 说明 |
|------|------|
| `ts` | 内核打点时的纳秒时间戳 (`ktime_get_real_ns()`) |
| `id` | 事件 ID（对应 schema） |
| `level` | 日志级别 (0=DEBUG, 1=INFO, 2=WARN, 3=ERROR) |
| `f` | 字段值数组，按 schema 顺序排列 |

### Schema JSON 格式

```json
// /vendor/etc/lcview_events.json （严格 JSON，禁止注释）
{
  "version": 1,
  "events": [{
    "id": 4,
    "name": "usb_transport_start",
    "desc": "USB bulk transport starts",
    "fields": [
      {"name": "device_index",    "type": "int64"},
      {"name": "data_direction",  "type": "int64"},
      {"name": "bytes_to_xfer",   "type": "int64"}
    ]
  }]
}
```

> **严格 JSON 模式**：`SchemaParser::parseJson` 设置 `allowComments = false`，禁止 JSON 注释（`//` 或 `/* */`）。内核和 daemon 共享 `lcview_events.h` 中的事件 ID 宏。JSON 文件定义字段名和类型，云端根据 ID 一对一建表。

## 过程视图

### 并发模型

Daemon 采用**单线程模型**：主线程同时负责 Binder 拉取、Schema 校验、文件写入。无需多线程同步，简化架构。

```plantuml
@startuml
autonumber
participant "main Loop\n(单线程)" as LOOP
participant "HAL (Binder)" as HAL
participant "SchemaParser\n(无锁)" as SCHEMA
participant "FileWriter\n(内部互斥)" as FW

note right of LOOP: 单线程模型\nBinder 拉取 + 校验 + 写入\n全部在主线程完成\n无需 mutex 同步

LOOP -> HAL : getBatch()
HAL --> LOOP : batch[]
LOOP -> SCHEMA : validate()
SCHEMA --> LOOP : true/false
LOOP -> FW : writeRecord()
FW -> FW : ofstream 写入
FW -> FW : 立即 flush
@enduml
```

**线程安全分析：**
- `SchemaParser::mSchemaMap` 仅在启动时加载，主循环期间只读，无需锁
- `FileWriter::mFiles` 仅在主线程访问，ofstream 本身无多线程写入，无需锁
- `gRunning` 使用 `std::atomic<bool>` 保证信号处理器与主循环的可见性

### 校验流程

每条二进制记录消费路径：

```plantuml
@startuml
start
:parse batch[offset] → total_len;
if (total_len < 4 || offset+total_len > batch.size?) then (是)
    :writeInvalid("bad length");
    stop
endif

:recordStart = batch[offset+4];
:recordDataLen = total_len - 4;

if (recordDataLen < sizeof(lcview_record_hdr)?) then (是)
    :writeInvalid("record too small");
    stop
endif

:schema.validate(recordStart, recordDataLen, errMsg);

if (magic != 0x4C56?) then (是)
    :writeInvalid("bad magic");
    stop
endif

if (event_id not in schema?) then (是)
    :writeInvalid("unknown event_id");
    stop
endif

if (field_count mismatch?) then (是)
    :writeInvalid("field count mismatch");
    stop
endif

:逐字段校验 type;
if (任何字段 type 不匹配?) then (是)
    :writeInvalid("type mismatch");
    stop
endif

if (总长度不匹配?) then (是)
    :writeInvalid("record length mismatch");
    stop
endif

:校验通过;
:es = schema.find(event_id);
:writeRecord(es, hdr, fields);
stop
@enduml
```

| 不变量 | 保证机制 | 代码位置 |
|--------|---------|---------|
| Schema 加载成功后主循环期间只读 | `SchemaParser::loadFromFile()` 成功后 `mSchemaMap` 不修改 | [`lechao_lcview.cpp:61`](../../code/rpi5/aosp/new/vendor/lechao/services/lechao_lcview/daemon/lechao_lcview.cpp#L61) |

### init 启动配置

```bash
# lechao_lcview.rc
on post-fs-data
    mkdir /data/vendor/lechao_lcview 0750 system system

service lechao_lcview /system/bin/lechao_lcview
    class main
    user system
    group system
    oneshot

on property:sys.boot_completed=1
    start lechao_lcview
```

| 配置项 | 值 | 说明 |
|--------|-----|------|
| `mkdir` | `/data/vendor/lechao_lcview 0750 system system` | post-fs-data 阶段创建父目录，init 自动 `restorecon` 打 SELinux 标签 |
| `class` | `main` | 随 main 类服务启动 |
| `user/group` | `system` | 以 system 身份运行，有限文件系统权限 |

| `boot_completed` | `sys.boot_completed=1` | 等待系统完全启动后再启动日志采集服务 |

### 目录自动创建

数据目录 `/data/vendor/lechao_lcview/` 由两层保障创建：

1. **init.rc 层**：`lechao_lcview.rc` 中 `mkdir /data/vendor/lechao_lcview 0750 system system`，init 阶段创建父目录并自动 `restorecon` 打 SELinux 标签
2. **C++ 兜底层**：`FileWriter` 构造函数中使用 `mkdirRecursive()` 递归创建 `logs/` 和 `uploaded/` 子目录（`mkdir -p` 等价实现），当父目录不存在时逐级向上创建

> **设计原因**：init 的 `mkdir` 只能创建路径的最后一级目录，POSIX `mkdir()` 同理。旧代码中 `mkdir(logDir.c_str())` 在父目录 `/data/vendor/lechao_lcview/` 不存在时静默失败（返回值被忽略），导致 `/data/vendor/lechao_lcview/logs/` 从未被创建。

## 关键设计与实现

本章节从架构与源码两个维度，提炼 Daemon 中的关键设计决策及其实现细节。

### Schema 重试 — 启动顺序解耦

**设计思路：** vendor 分区可能在 daemon 启动后才挂载完成，schema 文件 `lcview_events.json` 短暂不可访问。30 次重试（每次 500ms，最多 15 秒）替代旧版本直接 FATAL 退出策略，提高启动可靠性。

```plantuml
@startuml
start
:loadFromFile("/vendor/etc/lcview_events.json");
if (成功?) then (否)
    repeat
        :sleep 500ms;
        :retry++;
        :loadFromFile();
    repeat while (retry < 30?) is (是)
    ->否;
    :return 1 (退出);
else (是)
    :继续启动;
endif
stop
@enduml
```

**源码实现：**

```c
// lechao_lcview.cpp:60
int schemaRetry = 0;
while (!schema.loadFromFile(schemaPath) && schemaRetry < 30) {
    ALOGW("lechao_lcview: schema not ready, retrying... (%d/30)", ++schemaRetry);
    std::this_thread::sleep_for(std::chrono::milliseconds(500));
}
if (!schema.eventCount()) {
    ALOGE("lechao_lcview: failed to load schema from %s after %d retries",
          schemaPath.c_str(), schemaRetry);
    return 1;
}
```

### HAL 服务重试 — 启动顺序解耦

**设计思路：** HAL 进程可能在 daemon 启动后才注册 `vendor.lechao.lcview.ILcView/default` 服务。daemon 通过 `AServiceManager_checkService` + 100ms×1200 次重试循环等待服务就绪，而非 `waitForService`（NDK API 1.3.6 中不存在）。

**源码实现：**

```c
// lechao_lcview.cpp:88
auto bind_hal = [](const std::string& service) -> std::shared_ptr<ILcView> {
    AIBinder* raw = AServiceManager_checkService(service.c_str());
    if (!raw) {
        ALOGW("lechao_lcview: HAL not ready, retrying...");
        return nullptr;
    }
    ::ndk::SpAIBinder binder(raw);
    return ILcView::fromBinder(binder);
};

// lechao_lcview.cpp:107
int retryCount = 0;
while (!(hal = bind_hal(serviceName)) && retryCount < 1200) {
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    retryCount++;
}
```

### Pull 模式 — 无回调生命周期管理

**设计思路：** daemon 通过 `getBatch()` 主动拉取数据，而非 HAL push 回调。daemon 崩溃重启后直接调 `getBatch()` 无需重新注册回调，无 DeathRecipient 生命周期管理。daemon 处理慢时自然形成背压，数据在 HAL 队列中排队。

### 阻塞式 getBatch — 消除无效轮询

**设计思路：** HAL v2.3 将 `getBatch()` 从"立即返回空"改为阻塞等待（`condition_variable::wait_for 1s`）。数据到达时由 readerLoop 通过 `notify_one()` 唤醒，消除 daemon 端每 100ms 无效 Binder 轮询调用。

**源码实现：**

### Schema 驱动校验 — 拒绝损坏数据

**设计思路：** 每个事件 ID 对应固定字段 schema（JSON 配置），daemon 逐字段校验类型和数量。内核 ring buffer 可能出现数据错位、部分写入等异常，严谨校验防止损坏数据被写入 JSONL 文件。

```plantuml
@startuml
start
:接收二进制记录;
:find(event_id);

if (event_id not in schema?) then (是)
    :丢弃 + writeInvalid("unknown id");
    stop
endif

:validate(magic, field_count, types);

if (magic != 0x4C56?) then (是)
    :丢弃;
    stop
endif

if (field_count mismatch?) then (是)
    :丢弃;
    stop
endif

if (任何字段 type 不匹配?) then (是)
    :丢弃;
    stop
endif

if (record length mismatch?) then (是)
    :丢弃;
    stop
endif

:校验通过;
:写入 JSONL;
stop
@enduml
```

**源码实现：**

```c
// SchemaParser.cpp:148
bool SchemaParser::validate(const uint8_t* data, size_t len, std::string& errMsg) const
{
    if (len < sizeof(struct lcview_record_hdr)) {
        errMsg = "data too short for header";
        return false;
    }

    const struct lcview_record_hdr* hdr =
        reinterpret_cast<const struct lcview_record_hdr*>(data);

    if (hdr->magic != LCVIEW_MAGIC) {
        errMsg = "bad magic";
        return false;
    }

    const EventSchema* schema = find(hdr->event_id);
    if (!schema) {
        errMsg = "unknown event_id " + std::to_string(hdr->event_id);
        return false;
    }

    /* hdr->field_count 是 uint8_t，自然提升为 int 比较；
     * size() 直接比较防止 schema 字段数 > 255 时强转截断匹配 */
    if ((size_t)hdr->field_count != schema->fields.size()) {
        errMsg = "field count mismatch";
        return false;
    }

    // 逐字段校验类型 + 越界检查
    const uint8_t* ptr = data + sizeof(struct lcview_record_hdr);
    const uint8_t* const end = data + len;
    for (size_t i = 0; i < schema->fields.size(); i++) {
        uint8_t wireType = *ptr;
        uint8_t expectedType = static_cast<uint8_t>(schema->fields[i].type);
        if (wireType != expectedType) { ... }
        // string/binary 字段额外校验 fieldLen 不越界
        ...
    }
    return true;
}
```

### ostringstream 复用 — 减少堆分配

**设计思路：** `formatJsonLine()` 使用 `thread_local std::ostringstream` 复用，避免每次调用创建/销毁 `ostringstream` 的堆分配开销。`std::str("")` + `clear()` 重置流状态，不释放底层 buffer。

**源码实现：**

```c
// FileWriter.cpp:180
std::string FileWriter::formatJsonLine(const EventSchema& schema,
                                       const struct lcview_record_hdr* hdr,
                                       const uint8_t* fields,
                                       size_t fieldsLen)
{
    thread_local std::ostringstream oss;
    oss.str("");   // 清空内容
    oss.clear();   // 重置错误状态

    const uint8_t* ptr = fields;
    const uint8_t* const end = fields + fieldsLen;

    // 越界保护宏：读取前检查剩余空间
    #define LCVIEW_NEED(n) do { \
        if ((size_t)(end - ptr) < (size_t)(n)) { \
            ALOGE("out-of-bounds at field %zu", i); \
            return std::string(); \
        } \
    } while (0)

    oss << "{\"ts\":" << hdr->timestamp_ns
        << ",\"id\":" << hdr->event_id
        << ",\"level\":" << (int)hdr->level
        << ",\"f\":[";
    // 每个 switch case 读取前先 LCVIEW_NEED(类型大小) ...
}
```

> **NOTE**：`thread_local` 在此场景下等价于 `static`，因为 `writeRecord()` 仅在 daemon 主线程中被调用（单线程模型）。若将来多线程写入，`thread_local` 可保证每个线程独立，无需额外同步。

### mkdirRecursive — 递归创建目录

**设计思路：** Android 上 `mkdir` 不自动创建父目录，需要逐级创建。C++ 用户态程序不能依赖 shell 环境，递归实现更可靠。

**源码实现：**

```c
// FileWriter.cpp:34
static bool mkdirRecursive(const std::string& path, mode_t mode)
{
    if (path.empty() || path == "/") return true;

    std::string parent = path;
    while (!parent.empty() && parent.back() == '/')
        parent.pop_back();

    size_t pos = parent.rfind('/');
    if (pos != std::string::npos && pos > 0) {
        std::string parentDir = parent.substr(0, pos);
        struct stat st;
        if (stat(parentDir.c_str(), &st) != 0) {
            if (!mkdirRecursive(parentDir, mode))
                return false;
        }
    }

    if (mkdir(path.c_str(), mode) == 0 || errno == EEXIST)
        return true;

    ALOGE("FileWriter: mkdir %s failed: %s", path.c_str(), strerror(errno));
    return false;
}
```

### 立即 flush — 防止崩溃丢数据

**设计思路：** 每条记录写入后立即 `flush()`，防止进程崩溃导致缓冲区数据丢失。权衡性能与可靠性：高频场景下 flush 开销可接受，数据完整性优先。

**源码实现：**

```c
// FileWriter.cpp:279
it->second.stream << line;
if (it->second.stream.fail()) {
    ALOGE("FileWriter: write failed for event %u", schema.id);
    return;
}

it->second.stream.flush();
it->second.currentSize += line.size();
```

### LRU 淘汰 — 最旧文件优先删除

**设计思路：** 总日志量超限（500MB）时，按 mtime 从小到大排序，删除最旧文件腾空间。日志文件按日期命名，最旧的文件分析价值最低。

**源码实现：**

```c
// FileWriter.cpp:376
void FileWriter::enforceRetention()
{
    std::vector<LogFile> files;
    // 收集所有 .jsonl/.log 文件
    ...

    std::sort(files.begin(), files.end(),
              [](const LogFile& a, const LogFile& b) {
                  return a.mtime < b.mtime;  // 升序，最旧在前
              });

    size_t totalSize = 0;
    for (const auto& f : files)
        totalSize += f.size;

    // 从最旧文件开始删除
    for (const auto& f : files) {
        if (totalSize <= maxBytes) break;
        // 跳过当前正在写入的文件
        ...
        if (unlink(f.path.c_str()) == 0) {
            totalSize -= f.size;
            ALOGI("FileWriter: deleted old log %s", f.path.c_str());
        }
    }
}
```
